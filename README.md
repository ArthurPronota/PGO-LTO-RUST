# PGO и LTO в RUST


Твой конспект по PGO и LTO в целом верный и хорошо структурированный. Ниже — уточнения и дополнения, которые помогут избежать типичных ошибок и сделать материал точнее.

## LTO: что важно знать

### `fat` vs `thin`

Ты правильно пишешь, что `fat` медленнее, но иногда лучше. Стоит добавить практическую деталь: в реальных проектах разница между `thin` и `fat` по итоговой производительности часто **незначительна**, а по времени сборки — огромна.

Пример из реального PR в проекте Ruff: замена `fat` LTO на `thin` LTO **только для инструментальной сборки** (на этапе сбора PGO-профиля) сократила общее время PGO-пайплайна с ~738 секунд до ~338 секунд (на 54%), при этом размер финального бинарника и производительность не изменились. Финальная сборка всё равно использовала `fat`. Это хороший аргумент в пользу гибридного подхода: `thin` там, где скорость сборки важна, `fat` — для финального артефакта.

### `codegen-units = 1`

Ты упомянул, что это ограничивает параллелизм, но даёт больше контекста для оптимизаций. Это верно. На практике `codegen-units = 1` часто даёт **больший** прирост, чем сам по себе LTO, потому что позволяет LLVM видеть весь крейт как единое целое. Комбинация `lto = "fat"` + `codegen-units = 1` — стандартный «максимальный» профиль для production-сборок.

### Ожидаемый прирост

Твоя оценка «5-15%» для LTO — разумный ориентир. В некоторых бенчмарках (особенно на специфичных нагрузках вроде обработки пакетов) LTO в одиночку может не дать измеримого эффекта, если нет других условий (например, `#[inline]` для девиртуализации). То есть LTO — не волшебная таблетка, а один из факторов.

## PGO: уточнения по процессу

### Твой четырёхэтапный процесс — правильный

Инструментальная сборка → прогон → merge → финальная сборка. Всё верно. Пара практических замечаний:

1. **`cargo-pgo`** — удобная обёртка, которая автоматизирует эти шаги. Устанавливается через `cargo install cargo-pgo`, после чего процесс сводится к `cargo pgo instrument build` → прогон → `cargo pgo optimize build`. Это избавляет от ручного управления `RUSTFLAGS` и путями к `.profraw`.

2. **Путь к профилю**: в твоём примере `merged.profdata` — правильный подход. Но если профилей несколько (например, с разных сценариев нагрузки), их нужно объединять через `llvm-profdata merge`. Для одного прогона merge можно пропустить, передав путь к `.profraw` напрямую, но merged-файл обычно удобнее.

### Ожидаемый прирост

Ты пишешь «5-20% на хорошо профилируемой рабочей нагрузке». Это соответствует данным: PGO обычно даёт **дополнительные 5-10%** поверх `-O3 + LTO` на стабильной нагрузке. Для серверного кода с предсказуемым профилем трафика это действительно почти всегда оправдано.

### Когда PGO **не** стоит включать

- **Нагрузка сильно варьируется**: если приложение обслуживает и лёгкие запросы, и тяжёлые batch-задачи, профиль, снятый на одном сценарии, может ухудшить другой.
- **Нет репрезентативных данных**: «прогон на типичных данных» — критичный шаг. Если тренировочные данные не отражают production, профиль будет misleading.
- **Быстрая итерация**: PGO замедляет цикл сборки (два прохода + прогон), что может быть неприемлемо в разработке. Обычно PGO включают только для release-артефактов в CI.

## Практическая рекомендация по порядку включения

1. **Сначала `lto = "thin"` + `codegen-units = 1`** — это даёт большую часть выигрыша при разумном времени сборки.
2. **Затем PGO**, если есть стабильная нагрузка и возможность прогнать инструментальный бинарник.
3. **`lto = "fat"`** — если после профилирования видно, что именно кросс-крейтовый инлайнинг даёт дополнительный выигрыш, и время сборки не критично.

## Итог

Твой конспект покрывает суть корректно. Главные дополнения:

- `codegen-units = 1` часто даёт не меньший эффект, чем LTO.
- `thin` LTO для тренировочной сборки PGO может сэкономить время без потери качества.
- `cargo-pgo` упрощает процесс.
- PGO оправдан на стабильной нагрузке; на разнородной или быстро меняющейся — может навредить.
- Ожидаемые цифры: LTO 5-15%, PGO +5-10% поверх.
